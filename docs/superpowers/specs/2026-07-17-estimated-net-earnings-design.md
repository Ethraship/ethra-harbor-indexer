# Estimated Net Earnings API Design

Date: 2026-07-17

## Goal

Expose a stable user-facing earnings metric for the Morpho Vault indexer while
keeping the current indexed state model intact.

The current `lifetimeEarned` value is a mark-to-market calculation:

```text
activeDepositValue + lifetimeWithdrawn - lifetimeDeposited
```

Between vault interactions, Morpho performance fees can remain unminted. During
that window, `totalAssets` has increased but the admin fee shares have not yet
been minted into `totalSupply`, so the current mark-to-market value temporarily
overstates what the user will keep after the next fee-triggering interaction.

## Chosen Approach

Keep the existing fields and add a minimal derived-output layer in the
read-only API response.

The API will continue returning:

- `lifetimeEarned.raw`: current mark-to-market earned amount.
- `earnedPerformanceFee.valueRaw`: already-crystallized performance fee value
  attributed to this address.

The API will add:

- `grossLifetimeEarned.raw`: total yield generated by the address position.
- `estimatedNetLifetimeEarned.raw`: estimated user-kept earned amount after the
  expected 50% performance fee.
- `estimatedPerformanceFee.raw`: estimated total performance fee attributable
  to the address position, including crystallized and not-yet-crystallized fee.
- `blockContext`: freshness metadata explaining how estimated the net value is.

## Math

All math remains integer raw-USDC math.

```text
grossLifetimeEarned =
  lifetimeEarned + earnedPerformanceFeeValue

estimatedNetLifetimeEarned =
  grossLifetimeEarned * (10000 - performanceFeeRateBps) / 10000

estimatedPerformanceFee =
  grossLifetimeEarned - estimatedNetLifetimeEarned
```

For the current vault, `performanceFeeRateBps` is `5000`.

The subtraction form for `estimatedPerformanceFee` preserves every raw unit when
`grossLifetimeEarned` is odd. For example, a gross amount of `151` raw produces
`75` raw estimated net and `76` raw estimated fee.

If no share-price snapshot exists, these derived values return `null` raw
amounts because the API cannot value active shares or fee shares in USDC.

## API Shape

`GET /accounts/:address` will keep its existing fields and add:

```json
{
  "grossLifetimeEarned": {
    "raw": "150"
  },
  "estimatedNetLifetimeEarned": {
    "raw": "75",
    "performanceFeeRateBps": "5000"
  },
  "estimatedPerformanceFee": {
    "raw": "75"
  },
  "blockContext": {
    "currentBlock": 48750890,
    "lastProcessedLogBlock": 48750880,
    "lastPerformanceFeeMintBlock": 48750000,
    "blocksSincePerformanceFeeMint": 890
  }
}
```

`currentBlock` is the latest share-price snapshot block. That is the block used
for all valuation fields in the response.

`lastProcessedLogBlock` is the vault crawler cursor block. It tells clients how
far the local event log index has processed.

`lastPerformanceFeeMintBlock` is the latest indexed `AccrueInterest` event with
`performanceFeeShares > 0`. It marks the latest block where the performance fee
split became crystallized rather than estimated.

`blocksSincePerformanceFeeMint` is:

```text
currentBlock - lastPerformanceFeeMintBlock
```

If either block is unknown, it is `null`.

## User-Facing Semantics

The dashboard should use `estimatedNetLifetimeEarned` as the main "earned"
number.

It can show supporting context:

- `grossLifetimeEarned`: total yield generated by the position.
- `estimatedPerformanceFee`: estimated total fee attributable to that yield.
- `earnedPerformanceFee`: crystallized fee already observed from indexed vault
  logs.
- `blockContext.blocksSincePerformanceFeeMint`: how long ago the last
  non-estimated fee split occurred.

This keeps the visible earned amount stable before and after a fee-triggering
vault interaction. Before the interaction, pending fee is estimated. After the
interaction, the same economics appear as crystallized fee, with only small
timing and rounding differences.

## Implementation Notes

This design requires no schema migration for the core derived values.

Add one repository helper to read the last performance-fee mint block from
`accrue_interest_events`:

```sql
SELECT block_number
FROM accrue_interest_events
WHERE performance_fee_shares != '0'
ORDER BY block_number DESC, tx_index DESC, log_index DESC
LIMIT 1
```

Use the existing vault cursor helper for `lastProcessedLogBlock`.

Use the latest snapshot block for `currentBlock`.

The first implementation should keep the fee rate as a named constant in the API
query layer, because this indexer targets a single known vault. A later version
can replace that constant with an explicit config value or on-chain read if the
vault set expands.

## Testing

Add focused API/query tests for:

- gross lifetime earned equals `lifetimeEarned + earnedPerformanceFee.valueRaw`.
- estimated net and estimated fee split a gross odd value without losing raw
  units.
- block context reports latest snapshot block, cursor block, last nonzero
  performance-fee mint block, and blocks since mint.
- no-snapshot responses keep valuation-dependent derived raw fields as `null`.
